# edlr Journal 読み取り位置の永続化 + replay フラグ 設計書

2026-07-27 承認。デーモン起動のたびに現行 Journal ファイルを先頭から読み直す挙動をやめ、
読み取り位置を永続化して再開する。あわせて「デーモンが動き出す前に既に書かれていた
イベント」に `replay` フラグを立て、プラグインが自分の都合で扱えるようにする。

## 動機

現在の `JournalTailer` は `pos = 0` から始まるため、**デーモンを再起動するたびに
その日の Journal が丸ごと再配信される**。影響はプラグインの性質ごとに違う:

- アップローダ(`examples/plugins/inara-uploader`)は同じイベントを外部サービスへ
  二重投稿する。現在は「起動時刻より古いイベントを捨てる」回避策を入れているが、
  副作用として**デーモンが止まっていた間のイベントを取りこぼす**
- 通知・読み上げ系のプラグインは、数時間前のイベントを今起きたかのように処理する

どちらもプラグイン側では根本的に直せない(コアの再配信が原因)。位置を永続化すれば
両方消え、さらに停止中に書かれたイベントも保存位置から拾えるようになる。

## 中核の方針

- **位置の永続化はコアの責務**。プラグインに状態を持たせて回避させない
- **tailer はディスクに触らない**。位置の出し入れは `monitor` が担い、tailer は
  「復元された位置から読む」「現在位置を教える」だけにする(既存のテストしやすさを保つ)
- **保存は配信の後**。順序を逆にするとクラッシュ時にイベントが誰にも届かないまま
  失われる。at-least-once を選び、再配信分は `replay` で識別できるようにする
- **replay の境界は 1 本**: 「デーモンが動き出す前に既にファイルに書かれていたか」

## 責務の分担

| 置き場所 | 責務 |
|---|---|
| `core/src/journal/position.rs`(新規) | `PositionStore` — `<state-dir>/journal-position.json` の読み書き |
| `core/src/journal/tailer.rs`(変更) | 位置の復元と公開。ディスクには触らない |
| `core/src/monitor.rs`(変更) | 起動時に位置を読んで tailer へ渡し、poll のたびに保存する |
| `core/src/bin/edlr.rs`(変更) | `--state-dir` の解決と `PositionStore` の組み立て |

## 保存先と形式

`--state-dir` を新設する。既定は `$XDG_STATE_HOME/edlr`、未設定なら `~/.local/state/edlr`
(XDG 的に「状態」は config ではなく state)。ファイルは `journal-position.json`。

```jsonc
{
  "/home/himanoa/.../Frontier Developments/Elite Dangerous": {
    "file": "Journal.2026-07-27T120000.01.log",
    "offset": 48213
  }
}
```

- **Journal ディレクトリをキーにする**。Settings でディレクトリを切り替えても、
  別ディレクトリの位置を誤って適用しない
- 値はファイル**名**のみ(ディレクトリはキー側にあるため)
- 書き込みは既存の流儀どおり tmp + `fs::rename` で原子的に
- 古いエントリの掃除はしない(ディレクトリを変えるたびに 1 行増えるだけ)

## 行境界

現在の tailer は読んだバイト数ぶん `pos` を進め、行の途中で切れた部分は**メモリ上の
`partial` に保持**する。この `pos` をそのまま保存すると、再起動時に `partial` が失われ、
次の行が頭を欠いた状態で読まれる(パーサが警告して捨てる = イベントが 1 つ消える)。

**保存するのは `pos - partial.len()`**、つまり最後の完全な行の直後。再起動時はそこから
読み直すので、切れかけていた行も完全な形で読める。

## replay フラグ

**定義: デーモンが動き出す前に既にファイルへ書かれていたイベント。**

実装上は「起動後の最初の poll で読み切った分までが `replay = true`、それ以降の追記が
`false`」。厳密には起動直後の数百ミリ秒に書かれた行も replay 側に入りうるが、境界を
1 本に保つ価値の方が大きい(この誤差はドキュメントに明記する)。

この定義なら、初回起動の全読みも、保存位置からの再開分(= 停止中に書かれたぶん)も、
同じ規則で説明できる。

**`Status` イベントの `replay` は常に `false`。** Status.json は「今の状態」の
スナップショットで、過去分という概念が無い。

### プラグイン側の使い分け

- 通知・読み上げ系 → `replay` を無視する(数時間前のイベントを喋らない)
- アップローダ・集計系 → `replay` でも処理する(重複は位置の永続化が防ぐ)

## 型の変更

```rust
// core/src/event.rs
Event::Journal { timestamp, event, raw, replay: bool }
```

```wit
// core/wit/plugin.wit
record event {
  kind: string,
  timestamp: option<string>,
  name: option<string>,
  payload-json: string,
  replay: bool,
}
```

WS の JSON にも `"replay": true/false` を足す(UI が将来「過去分」を畳めるように。
今回 UI 側の変更はしない)。

### ABI 破壊と移行

`record` にフィールドが増えるため、**旧 world でビルド済みのプラグインバイナリは
インスタンス化に失敗する**。

- **WIT パッケージのバージョンを `edlr:plugin@0.1.0` → `@0.2.0` に上げる**。非互換を
  明示するため。旧プラグインは「`edlr:plugin/host-log@0.1.0` が見つからない」で明確に
  失敗し、既存の仕組みでそのプラグインだけが `Disabled`(理由付き)になる
- リポジトリ内の 2 例(`hello-logger` / `inara-uploader`)は再ビルドが必要。Go 側は
  コミット済みバインディング(`gen/`)の再生成も必要
- 第三者プラグインはまだ存在しないため、互換 shim は設けない

## 異常系

| 状況 | 挙動 |
|---|---|
| state ファイルが無い・壊れている | 位置なしとして扱う(現行ファイルを先頭から読み、全て `replay = true`) |
| 保存したファイルがもう存在しない | 名前順で**その次のファイル**の先頭から再開。無ければ**現在位置より厳密に新しい**最新ファイルの先頭から。それも無ければ位置を据え置き、次の poll で再試行(より古いファイルへ巻き戻すと、そこから全ファイルを読み直して `replay = false` で再配信してしまう) |
| 保存した offset がファイルサイズより大きい | そのファイルを先頭から読み直す(既存の truncate 検出と同じ) |
| state ディレクトリに書けない | warn を 1 度出して動き続ける。位置が動くたびに再試行し、書けるようになれば黙って成功に戻る(それまでは現状の挙動に劣化するだけ) |
| 同じ Journal ディレクトリを 2 つのデーモンが見ている | 後勝ちで上書き。サポート構成ではない旨をドキュメントに書く |

**ファイルの同一性は名前だけで判断する**(inode は見ない)。Journal は追記専用で
ローテーションも名前順、という前提が既存コードにあり、ここだけ inode 追跡を持ち込むのは
複雑さに見合わない。同名別ファイルへの置き換えは「offset > サイズ」で先頭から読み直す
形で拾う。

## テスト方針

- **`PositionStore`**: 保存 → 読み込みの往復、壊れた JSON は「位置なし」扱い、
  書き込み不能でも panic せずエラーを返す、Journal ディレクトリごとにキーが分かれること
- **`JournalTailer`**: 途中位置からの再開、保存 offset > ファイルサイズ → 先頭から、
  保存ファイルが存在しない → 名前順で次のファイルの先頭から、**行境界の保存**
  (`partial` を含む位置を保存しない = 再起動後に頭を欠いた行が出ない)、
  **replay の境界**(最初の poll で読んだ分が `true`、その後の追記が `false`)
- **`monitor` 統合**: 起動 → 位置保存 → 再起動で同じイベントが 2 回配信されないこと。
  デーモン停止中に追記されたぶんが `replay = true` でちょうど 1 回届くこと
- **イベント / WS**: WS JSON に `replay` が載ること、`status` イベントは常に `false`
- **実 wasm**: `plugin_host_integration` で、プラグインが受け取る `event` に `replay` が
  渡ること
- **既存プラグイン**: `hello-logger` が新 world で再ビルドできること、`inara-uploader` の
  バインディング再生成後にビルドできること

## スコープ外

- UI での replay の表示(WS にフィールドは出すが Logs 画面は変更しない)
- inode ベースのファイル同一性追跡
- 同一 Journal ディレクトリを複数デーモンで見る構成の排他制御
- Status.json の位置永続化(スナップショットなので不要)
- 旧 world(`@0.1.0`)のプラグインを動かすための互換 shim
- 位置マップの古いエントリの掃除
- `Market.json` / `Cargo.json` の監視追加(別件)
